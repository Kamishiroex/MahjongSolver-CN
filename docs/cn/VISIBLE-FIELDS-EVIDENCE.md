# Emj 其余可见字段：候选定位与读取边界

调查日期：2026-09-23。国服客户端 `2026.09.15.0000.0000`；ClientStructs `f824354f4a6a2b1cd16cc8fcb670c7a66bf64880`；Lumina `cb3511aa350b72b5112d740fbe3a522d305fd808`；上游 `21ae5ca9aa1fa3785baa540245b51efa346f9d37`。本文件是下一阶段的读侧证据，**没有新增生产读取路径或启用完整牌局建议**。

## 结论

下方自家牌面已有资源身份检查及用户静止画面的逐张、顺序核对。其他字段目前最接近可扩展诊断的是**下方右侧的副露候选组件**和**桌面四侧的点棒图像**。它们仍缺少完整动态语义验证，不能直接填入 `OurMelds` 或 `Riichi`。

点数、座风存在范围很小的文本候选，但资源并未标注语义，旧诊断只记录长度。读取这些文本前应先通过候选框定位和用户对照确认字段，避免误采相邻名字。局风/局数尚无足够可靠的节点定位。摸牌独立槽 `135` 是强候选，但动画样本反驳了“总数多一张或最右一张就是摸牌”的简化假设。

| 字段 | 当前证据 | 可交付状态 |
| --- | --- | --- |
| 自己的下方立牌 | 原有 shell/face 白名单、资源哈希、用户静止画面对照 | 限定样本实测支持；不代表完整牌局读取 |
| 自己的副露 | 静态四牌组合、下方区域、实际生成的两个组件组 | 结构定位已有依据；牌面、类型、来源座位待验证 |
| 自己及各家点数 | 四个头像面板中的小范围文本候选，长度一致 | 待验证，当前不读文本 |
| 门风/座位 | 同四面板各一个 120×18 文本候选 | 待验证，当前不读文本 |
| 立直 | 桌面四侧相同点棒图片模板 | 可增加点棒图像诊断；立直语义待验证 |
| 局风、局数、本场、供托 | 只有未定名文本/数字布局候选 | 待验证，不指定未经证明的语义节点 |
| 摸牌身份 | 独立节点 135 与相同位置占位组件 136 | 可显示“独立槽候选”；不能据此启用摸切或役判断 |

## 自家副露候选

静态根节点 `112`：模板 `1060`，大小 140×55；父链 `112 → 111 → 46 → 1`。在 ULD 下方布局的 y=640，与自家立牌同排、位于右侧。模板 1060 包含：

| 组件内节点 | 模板 | 静态位置/旋转 | 内部牌面与壳 |
| --- | --- | --- | --- |
| `2` | `1055` | (-42,0)，不旋转 | `/9` 是 1010；`/9/4` face、`/9/5` shell，与已验证下方立牌相同 |
| `3` | `1055` | (0,0)，不旋转 | 同上 |
| `4` | `1056` | (42,12)，270° | `/9` 是 1013，不是 1010 |
| `5` | `1056` | (42,-30)，270° | 同上，用于上下叠置的结构候选 |

模板 1013 中 face 图像 4 使用动态 parts list 0，40×52，但静态 `ScaleX=-1`、Origin=(18,23)；shell 图像 5 使用 EmjTile 的 parts list 18、part 0、42×55，Origin=(21,27)。因此不能用“允许任意旋转/缩放”的方式复用手牌读取器，也不能只看 leaf 的 Rotation=0 就忽略其父组件旋转。明杠/加杠/暗杠的显示还需核对遮挡、叠置、背面与正面。

第三包有 61 帧同时出现 `Emj/112` 和运行时克隆 `Emj/1120001`，均为 1060。各组的 `/2/9/4`、`/3/9/4` 和 `/4/9/4` 可见，`/5` 组件存在但对应 `/5/9/4` 未出现。它证明该版本确实使用这个显示结构；没有采集这些 face 的 IconId，因而不能恢复牌面、判定吃或碰，或确认鸣牌来源。ULD 本身没有根 1120001，克隆编号依据是此次诊断，不应由编号规律任意扩大范围。

可做的最小下一阶段：只标注两个已观察根的屏幕范围，让用户确认是否为自己的副露。若确认，再对每组未旋转 `/2`、`/3` 单独复用原有严格 shell guard 和 face 资源检查，显示为“不完整副露候选”以供核对。完整副露解析仍需为 1056/1013 建立有限、明确的旋转和叠牌规则，并补吃、碰、明杠、暗杠、加杠样本；未完成前不能据两张牌补猜第三张。

另外，底部根 `128` 的 `129..131` 模板 1012、`132` 模板 1011 使用 EmjTile part 6 的背面图像。它们不是已证实的副露牌面来源，应继续排除。

## 点数与座风文本候选

四个面板的结构关系已经确认，但下面“点数/座风”只是定位候选，不能称为实际内容读取结果：

| 面板根 | 静态模板/父链 | 点数候选文本 | 门风候选文本 | 必须排除的邻近文本 |
| --- | --- | --- | --- | --- |
| `38` | 1026；38→37→36→1 | `38/12/2`、`38/12/3`；模板1047 | `38/9` | `38/5`、`38/6` |
| `40` | 1025；40→39→36→1 | `40/13/2`、`40/13/3`；模板1047 | `40/10` | `40/6`、`40/7` |
| `42` | 1025；42→41→36→1 | `42/13/2`、`42/13/3`；模板1047 | `42/10` | `42/6`、`42/7` |
| `44` | 1025；44→43→36→1 | `44/13/2`、`44/13/3`；模板1047 | `44/10` | `44/6`、`44/7` |

1047 的两个文本节点静态位置相同，均为 108×20；候选门风文本为 120×18。第三包所有 75 帧中，各 1047 文本 2 的 `TextByteLength=5`、文本 3 为 6，各门风候选长度为 3。上述邻近 208×14 文本位于面板顶部，可能承载名字，绝不读取其内容。长度只能支持“该处有短文本”的观察，不能把 5/6 字节解释成点数，或把 3 字节解释成一个风字。

最小定位方式是用已有位置元数据绘制候选框，用户只勾选框是否对应游戏中的点数/门风，不采集截图、名字或其他文本。明确确认后才开放精确节点的有界文本读取：点数只接收严格数字格式；门风只接收精确四值枚举；任何其他内容仅记录拒绝码，原文不进入日志。枚举与数值还需同一帧关联确认、换局确认、分数变化确认，不能凭正则格式就宣告语义正确。

文本读取结构应使用固定 [AtkTextNode](https://github.com/ottercorp/FFXIVClientStructs/blob/f824354f4a6a2b1cd16cc8fcb670c7a66bf64880/FFXIVClientStructs/FFXIV/Component/GUI/AtkTextNode.cs) 和 [Utf8String](https://github.com/ottercorp/FFXIVClientStructs/blob/f824354f4a6a2b1cd16cc8fcb670c7a66bf64880/FFXIVClientStructs/FFXIV/Client/System/String/Utf8String.cs)。第一包的 StringLength=0 不能解释为画面没有文本，详情见 LOWER-HAND-EVIDENCE；当前长度来源是 BufUsed。还需处理 UI 文字控制序列，不能直接从任意字节中抽取数字。

## 立直点棒候选

根 `100/101/102/103` 均为模板 1037，父链经 99→46→1，分别位于桌面下、右、上、左。1037 的图像节点 `/2` 是 78×12，parts list 14、part 4，资产 17 `ui/uld/EmjParts.tex`，UV=(0,36)、78×12。本机静态图像在该位置是红色一点的点棒。上方供托区域和结算界面也复用点棒部件，因此只有精确父链可以限定四家桌面候选，不能全 addon 搜索相同贴图。

第三包所有 75 帧都含这四个父组件，**没有一帧包含其可见 `/2` 图像**。父组件可见不能当成已经立直；图像不存在也不能立即推断“未立直”，因为仍需排除动画、刷新间隙和局界。

可增加的窄诊断：只检查这四个根下 `/2` 的完整可见链、选中 part、UV、尺寸和 `TexPathHash`；不读取文字、牌面或任何未知内存。记录“点棒当前可见/不可见/结构异常”，由一次手动立直前后和下一局消失的样本确认语义，再把屏幕方向转换到已经验证的门风顺序。点棒贴图本身不是一个足以同时证明立直成立时点、一发有效期和供托数量的字段。

## 局数与中央数字

模板 1016（根 `105`）包含两个 1064 子组件，它们各有 type 5 数字节点；实际路径是 `105/2/2` 和 `105/3/2`。当前包 75 帧都存在这两个数字节点。固定 [AtkCounterNode](https://github.com/ottercorp/FFXIVClientStructs/blob/f824354f4a6a2b1cd16cc8fcb670c7a66bf64880/FFXIVClientStructs/FFXIV/Component/GUI/AtkCounterNode.cs) 有独立 `NodeText`，不是 AtkTextNode。虽然静态 `Emj_Number.tex` 显示数字字形，这仍不能确定它是剩余牌数、计时、局数或其他数字，因此不把它当成局数。

上方 `22/23/27` 等文本同样没有 ULD TextId 标签可证明语义；本 ULD 检查的 TextNode.TextId 均为 0，文字由运行时填入。不能直接借用英文客户端位置或根据字节长度给出场风、局数、本场、供托映射。下一步应先定位正常界面上的这些标签，再建立有界字段白名单。

## 摸牌身份与过渡状态

静态下方 `134`、`135` 使用同一 1055 模板，父链经 133→46→1；135 是独立组件，旁边 `136` 是 1019，占位图像使用 EmjTile part 1。原有诊断已限定 135 的 face 读取。

第三包的结构组合如下。“候选数”包括被拒绝的候选，不能视为合法牌数；组数只是 1060 组件数，不能视为已确认副露数。

| 下方候选数 | 1060 组数 | `135/9/4` 可见 | `136/2` 可见 | 帧数 |
| --- | --- | --- | --- | --- |
| 0 | 0 | 否 | 否 | 14 |
| 7 | 2 | 否 | 是 | 38 |
| 8 | 2 | 否 | 是 | 5 |
| 8 | 2 | 是 | 是 | 17 |
| 9 | 2 | 是 | 是 | 1 |

这些组合说明不能按列表末尾、总数取模或 135 父组件存在来填 `DrawnTile`。可以保留“来自独立槽 135”的渲染身份，并在用户明确标记摸牌前后、排序前后、吃碰后无摸牌出牌的样本中核对。补杠摸牌、立直自动摸切和动画重复尚无覆盖，摸牌语义仍是未知。

## 上游和 ClientStructs 能提供什么

固定上游 [BaseEmjVariant](https://github.com/XeldarAlz/FFXIV-AutoMahjongSolver/blob/21ae5ca9aa1fa3785baa540245b51efa346f9d37/Mahjong.Plugin.Dalamud/GameState/Variants/BaseEmjVariant.cs) 用 JSON 私有偏移读分数/手牌，把座位、场风写成常数，并把各家立直设为 false。它没有可直接用于此国服版本的上述 UI 字段定位证据。

[MeldTracker](https://github.com/XeldarAlz/FFXIV-AutoMahjongSolver/blob/21ae5ca9aa1fa3785baa540245b51efa346f9d37/Mahjong.Plugin.Dalamud/GameState/MeldTracker.cs) 根据手牌减少和弃牌计数推断副露；吃牌两张连续时存在第三张歧义，代码选一个方向。它不是副露 UI 读取器。国服必须确认组成与来源，不能因已有两张相邻牌便采用该猜测补齐。暗杠/加杠还含动作路径上的手工记录，不适合作为重新启用插件后恢复完整局面的依据。

固定 ClientStructs 的 [Client.Game.UI.Emj](https://github.com/ottercorp/FFXIVClientStructs/blob/f824354f4a6a2b1cd16cc8fcb670c7a66bf64880/FFXIVClientStructs/FFXIV/Client/Game/UI/Emj.cs) 只是大小 0x38 的空声明；没有可用牌局字段。[EmjModule](https://github.com/ottercorp/FFXIVClientStructs/blob/f824354f4a6a2b1cd16cc8fcb670c7a66bf64880/FFXIVClientStructs/FFXIV/Client/UI/Misc/EmjModule.cs) 是用户显示设置，不能当成当前桌牌局结构。虽然公开枚举包含 Emj 的 NumberArray/StringArray 标识，它们没有各槽语义，不应批量采集未知数组内容。

## 下一轮新增的副露元数据

已新增纯范围定义 `LowerMeldMetadataProfile`，尚不能把它当成读取器本身：

- 只匹配 `Emj/{112|1120001}/{2|3|4|5}/9/{4|5}`，leaf 必须是 Image；没有观察到的 `1120002` 等编号不自动允许。
- 返回根类型 1060、精确父 ID 链 111→46→1，以及需要由调用者实际核对的 1060→1055/1056→1010/1013 路径类型。只匹配字符串不算验证通过；真实 leaf 父链必须经过同一个 group 对象再到 addon 根。
- 对 `/4` face 只复制已经允许的 `AtkResNode` 元数据，**不读取 AtkImageNode 头、parts、asset、IconId、hash 或路径**。
- 对 `/5` shell 可额外读取当前 `PartId`、parts list ID/count 及当前选中项的 U/V/Width/Height；不枚举其他 part，不解引用其 asset，不读任何纹理资源。
- 记录 leaf 及完整父链的 NodeId/Type、ScaleX/Y、Rotation（运行时弧度）、OriginX/Y、2×2 Transform 和 Width/Height，不导出地址。链最大 16 项；隐藏、循环、归属不符、非有限数值或链不完整时拒绝选中部件读取，给出拒绝位置。

这会新增旧包缺失的镜像、旋转中心、矩阵和壳 part 数据，能直接核对 1013 的翻转及加杠叠置；不是只重录旧有位置和尺寸。有限的非单位矩阵可以作为诊断数据，但并不授权读 face 资源。版本/ULD 精确检查、用户显式开关、预算和 scene 退出停止仍由外围读取器负责。

纯 profile 的 38 项离线测试已在独立临时测试工程运行通过：覆盖两个已观察组、全部四个分支、face/shell 分离、错误类型、未知克隆、其他方向、非规范路径及可变数组隔离。这些测试验证范围限制，不证明真实父链或副露语义。生产测试工程的链接与读取器接入由主实现统一完成。

## 最少下一步

1. 0.1.2.0提供已限定的下方牌面中文识别与稳定画面对照；其他字段继续 unknown，建议和自动操作关闭。
2. 已接入上述副露元数据与其他公开布局范围，未实现候选框或未验证文本内容读取。四面板的点数/门风、四侧点棒仍需明确定位证据，不能误称已采集到语义。
3. 用户一次开始整场本地记录后正常打NPC，尽可能覆盖副露形成、横置、叠杠、立直和换局；停止自动打包，开发者在同机直接分析完整会话和已有事件记录，无需逐字段更新后反复导出。没有实际出现的特殊情况继续待验证。
4. 给旋转副露、暗杠和加杠各自建立覆盖/背面保护，不放宽现有手牌 guard。完整数据与来源关系通过后再接引擎，牌局读取正确性与建议质量仍分别验收。
