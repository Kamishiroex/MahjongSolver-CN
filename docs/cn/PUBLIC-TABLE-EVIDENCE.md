# 公开牌桌区域：固定结构及第三、第四次诊断证据

下方第三包调查记录保留其原始范围。第四包已验证其中实际采到的父链/壳矩形，并发现后续克隆覆盖不足；新增范围、容量修复和局部平移字段见文末及 [第四份分析](FOURTH-CAPTURE.md)。这些仍是结构证据，未读取牌河或宝牌牌面。

本次研究只读取本机固定公开资源和第三次诊断 ZIP 内的布局元数据；没有解包或公开原始报告，没有读取其他三家的暗手资源/内容，也没有调用游戏原生函数。新增 `PublicTableMetadataProfile` 只提供纯托管路径/类型门，不自行读取内存。下述“牌河”和“宝牌区”是结合静态位置与运行布局划定的候选区域，尚未实测牌义。

例如静态链为 `118 -> 116 -> 46 -> 1`；各图像位于组件模板内部，内部父链为 `图像 4/5 -> 容器 3 -> 容器 2 -> 模板根 1`。采集器目前生成的 `Emj/118/4` 是**省略普通节点祖先的显示路径**，不能替代实时指针父链和组件归属验证。

模板 1021/1022/1023/1024 均有：

- `/4`：type 2 Image，40×52，ScaleX/ScaleY=0.78；静态 PartList=0、PartId=0，是动态牌面候选，不是固定图标 ID。运行时必须校验当前 PartId 在当前 PartCount 内，只能读取选中的 Part。
- `/5`：type 2 Image，34×45，是静态壳；与 `/4` 同属容器 3。模板节点 2、3 均为 type 1。

正面壳的静态契约如下；均使用 PartList 18（23 项）、Asset 21、`EmjTile.tex`：

本地图集中 Part 18/20 是浅色正面壳；Part 21（132,46,34,45）和 Part 22（97,46,34,45）是背色区域。**上述只是静态选择，第三包没有读取这些运行壳的 Part/Asset/hash。** 下一次诊断必须先验证对应正面壳、类型、矩形及标准路径 CRC，失败时不能读取 `/4` 的图标或资源 hash。壳 CRC 应复用已纠正的[标准 CRC 约定](TEXTURE-HASH-EVIDENCE.md)，不能使用 Lumina 的未取反返回值。

另一个静态根节点可能服务横置牌等显示，但尚无第三包出现记录，不能直接标成“立直宣言牌”。同样不能假定 clone 编号就是弃牌先后次序。

## 右上方五格：显示的是宝牌还是指示牌

静态根节点 `28..32` 都是模板 1006，精确父链为 `28..32 -> 26 -> 21 -> 1`；26、21 为 type 1。根局部 X 分别为 54/98/142/186/230，Y=18，尺寸 50×60，ScaleX/ScaleY=0.75。

1006 内部结构不同于手牌和牌河：

- `/2` 为 type 2 动态 Image，父为模板根 1；位置 (5,4)、40×52，静态 PartList=0、PartId=0。
- `/3`、`/4` 均为 **type 4 NineGrid**，同属模板根 1。它们使用 `EmjParts.tex` 的 Asset 17：PartList 14 的 Part 26（79,65,18,18）和 Part 27（76,122,18,18）。这些是边框结构，**不是正反面壳**，不能把 `/4` 当动态牌面或套用 `/5` 壳规则。

第三包仅实际出现 `Emj/28`、`/28/2`、`/28/3`、`/28/4`，在 seq 144..204 的 61 个保留帧中出现。29..32 未出现只表示未被该次可见节点采集保留，不能填成空牌或推断整局恰有一个指示牌。本次尚无此区域运行图标/Part/hash，公开归属仍须与游戏正常显示逐格确认。1006 缺少已验证正反壳门，应先单独完成区域归属及隐藏槽位验证，再允许受控 `/2` 诊断；不要扩大手牌读取器白名单后直接复用。

本机中文公开资源提供明确的模式差异：`Addon` 行 12434 为“宝牌指示牌设置”，12435/12436 为“多玛式”/“传统式”；12437 说明多玛式直接显示宝牌，12438 说明传统式显示的牌的下一张才是宝牌。对应固定资源：

- `exd/addon.exh` SHA256：`079183FA8D82889F6C486B7F62E9CD0178A5B77E9DD88927405692755CE6DBE8`。
- `exd/Addon_0_chs.exd` SHA256：`2D41452BCC4414F9B84D003B4F1E354A913028647C809383C4C0421924C5509F`，读取 `Addon` 的上述 RowId、字符串列 0 可复核。这里是公开帮助文本，不是运行 UI 文本采集。

固定 [ClientStructs 的 EmjModule](https://github.com/ottercorp/FFXIVClientStructs/blob/f824354f4a6a2b1cd16cc8fcb670c7a66bf64880/FFXIVClientStructs/FFXIV/Client/UI/Misc/EmjModule.cs) 定义了 `ShowTraditionalDoraIndicator`（0x50）及 `TileSet`、`ShowHighResolutionLayout`，但本次没有读取其运行值，未调用 `Instance()` 或 `GetEmjModule()`。字段名本身不能证明第三包的选中模式。

下一次应将 `DoraDisplayMode` 分成 `Unknown`、`ActualDora`、`Indicator`，先通过普通设置界面及同一局切换前后的受控公开显示核对，再验证字段与界面的一致性。模式未知时停止宝牌推导；多玛式输出不能直接塞入引擎 `DoraIndicators` 后再计算下一张，否则会再次偏移。观察到的显示牌与以后可能推导的数据应分别保存，不能把推导结果写成“实读指示牌”。切换模式或牌面样式也必须清除旧建议并重新建立稳定状态。

## 有依据的下一阶段

已准备纯托管 `PublicTableMetadataProfile.TryMatch`，供独立的**公开牌桌布局诊断**使用：只匹配表中已观察的牌河根/clone、`/4` 和 `/5`，以及静态确认的宝牌根 28..32、`/2`、`/3`、`/4`。读取器参数默认关闭，0.1.2.0起窗口预选该项且只有用户开始后才采集。`ReadShellPart` 仅牌河 `/5` 为 true；其他匹配只能记录变换，不能读取面资源。牌河叶节点还要求同根下 `/2`、`/3` 为 type 1，实际祖先链必须经过正确 root 地址，再验证对应区域 owner 链。未观察的横置替代根仍拒绝。

本轮拟集成的 0.1.2.0 只增加公开布局变换、实际父链 ID/type 和当前选中**壳** Part 的 ID/list/count/UV/尺寸诊断；不解引用 Part.Asset，不读取任何新增区域的 face IconId/hash，也不扩大手牌白名单。宝牌 NineGrid 本轮只记录变换。只有后续确认实际公开归属、正面壳与几何门后，才可另行设计逐区图像核对。其他三家暗手所在的 137/140/143 区域始终排除。

仍需覆盖新弃牌追加、换行、被鸣牌位置、立直横置牌、四方旋转、退桌/换局以及宝牌两种显示模式。当前证据足以缩小下一次诊断范围，**不足以宣称牌河或宝牌读取正确，也不允许开放建议或自动操作**。

## 第四包补充与0.1.2.1范围

在相同客户端、ULD和框架身份下，第四包实际观察到常规根及连续克隆：1180001..1180014、1210001..1210015、1240001..1240014、1270001..1270014，类型仍与表格对应。旧白名单之外新增36个克隆仅有基础节点观察，未采到完整增强父链；0.1.2.1只将这些精确范围纳入元数据候选，继续现场验证，不外推更多编号或横置替代根。

已采到的5441个牌河壳部件均符合表中正面矩形。7391个相对位置样本符合旋转后的六列布局（列间34、行间45），但克隆位置不等于完整弃牌历史；鸣牌移除、横置和换局未验证。另有3帧、6条增强牌河记录出现祖先容器约1.03的临时缩放，说明将来判稳定必须包括祖先变换。

扩充后的可匹配节点同帧峰值为199，静态白名单理论上限219，元数据条数上限改为256；原总节点、读取次数和采样时间上限不变。依据固定Dalamud `NodeBounds.cs`，附加记录已读取基础结构中的局部X/Y，以支持完整祖先变换的后续检查；旧记录缺少时保持null。此修改没有增加任何公开区域牌面、资源哈希或文本读取，也不能由旧日志补出未采的数据。
